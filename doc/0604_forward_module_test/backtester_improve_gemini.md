这是一个非常专业且敏锐的量化工程问题！

从“流式按天循环（在线回测）”切换到“按股票遍历（批处理落盘）”，虽然能带来 100 倍以上的速度提升，但**必然会在底层数据对齐上产生微小的差异**。你提到的“15分钟数据”正是其中最典型的一个坑。

如果直接按照 `backtest_improve_qwen.md` 的架构去写 `signal_generator.py`，你会在以下 **4 个维度**遇到与之前全日历回测不完全一致的差异。我为你逐一剖析，并给出消除差异的解决方案：

---

### 差异 1：15 分钟数据的“历史真空”与对齐机制（你最担心的点）

**原理差异：**

* **老系统（流式）**：当系统跑到 `2025-08-01` 这一天，它会去读取当时的 `15m` 数据。由于通达信（VIPDOC）的 `.lc5` 数据通常只保留最近 1~3 个月，老系统在测 2025 年时，15分钟数据直接返回空，`M15_U` 默认为 0。
* **新系统（批处理）**：你现在（2026年6月）一次性读取了某只股票的全部数据。如果你试图把当前的 15分钟数据（只有 2026年3月-6月）硬塞进整个 DataFrame，或者用 `merge`/`join` 拼接，很容易导致时间戳错乱。

**影响程度：微乎其微（得益于你的 P0 改造）。**
因为你在之前的 P0 改造中，已经把基础分拔高到了 95 分，15分钟数据（`M15`）变成了“锦上添花”而不是“雪中送炭”。所以缺失 2025 年的 15m 数据，**不会导致选股漏单**。

**如何避免差异（代码建议）：**
在 `signal_generator.py` 中，计算 `M15` 因子时，必须加入**时间戳硬对齐**。

```python
# 伪代码：在循环某一天时，安全获取当日的 15m 状态
if date >= min_data_start_date: # 如果这一天在近3个月内，有15m数据
    m15_slice = min_df[min_df.index.date == date.date()]
    # 计算 M15_U ...
else:
    m15_features = {'M15_U': 0, 'M15_L': 0, 'M15_H': 0} # 历史真空期，安全赋 0

```

---

### 差异 2：最大的隐形杀手 —— 前复权（Forward Adjustment）的“锚点漂移”

这是所有量化系统从流式转批处理时都会遇到的最核心问题。

**原理差异：**

* **老系统**：每天都在“假装”那是当前的最新一天。比如跑到 `2025-05-01`，系统会用 `2025-05-01` 的收盘价作为基准向后做“前复权”。
* **新系统**：你现在一次性拉取了股票数据，系统会以 **当前最新日（2026-06-04）** 作为基准，对整个历史数据做前复权。

**产生的影响：**
如果一只股票在 2025年9月 进行了分红派息（除权），那么：

1. **老系统**在测 2025年8月时，看到的价格是 **真实价格**（比如 10 块）。
2. **新系统**现在看 2025年8月，看到的价格是被 9 月份除权**向下修正过的价格**（比如 9.5 块）。
3. **结果**：你落盘到 `master_signals.csv` 里的 `trigger_buy` 价格，会和老系统算出来的价格对不上！

**为什么不用担心：**
你的策略核心是 `MACD`、`MA20` 乖离率（`B20`）和 `RSI`。这些指标都是**比例型/动量型指标**，对绝对价格免疫。10块跌到8块，和9.5跌到7.6，算出来的形态、顶底背离、分数是 **100% 一致的**。
**解决方案**：接受这种绝对价格的差异。实盘时永远看最新价格，回测时看复权价格，只要盈亏比（%）一致即可。

---

### 差异 3：EMA/MACD 指标的“预热期 (Warm-up)”精度差异

**原理差异：**

* **老系统**：每天截取一段（比如过去 150 天）的数据计算 MACD。由于 EMA（指数移动平均）是无限追溯权重的，只用 150 天算出来的 MACD，会有微小的精度截断误差。
* **新系统**：`compute_indicators(df)` 会直接用股票上市以来的所有数据一次性算出 MACD，EMA 的平滑权重吸收得极其完美。

**产生的影响：**
**新系统算出来的指标比老系统更精准！** 极个别在老系统中“处于金叉边缘（差 0.001）”的股票，在新系统里可能会变成真正的金叉或死叉。这可能导致总信号数量有 1% ~ 2% 的出入，但这属于“修复了老系统的误差”，是好事。

---

### 差异 4：未来 7 天 (Forward 7D) 遇到“停牌”的对齐

在老系统中，`FORWARD_DAYS = 7`。如果是流式计算：

* **老系统**：买入后，向后数 7 个**全市场交易日**。如果这只股票这 7 天停牌了，那它的收益就是 0。
* **新系统**：如果你用 `forward = df.iloc[idx+1 : idx+8]`，你截取的是**这只股票自己的下一个 7 根 K 线**。如果它停牌了半年，你截取到的其实是半年后复牌的那 7 天！这就引入了**未来函数**。

**如何避免差异（代码建议）：**
在 `signal_generator.py` 截取未来 7 天数据时，**绝对不能用 `iloc`，必须用基于全市场交易日历的切片**。

```python
# ❌ 错误写法（会跨越停牌期，引入未来函数）
# forward_data = df.iloc[current_idx + 1 : current_idx + 8] 

# ✅ 正确写法（严格按市场真实日历截断）
market_next_7_days = trading_days[trading_days > date][:7]
# 只在股票数据中提取这 7 个真实日期的数据，没有（停牌）就是 NaN
forward_data = df.reindex(market_next_7_days) 
future_mfe = (forward_data['high'].max() - entry_price) / entry_price

```

### 总结

这种架构升级带来的差异是**必然且良性的**。量化界有一句名言：“没有 100% 对齐的流式和批处理，只有逻辑等价的架构”。

**只要你在写 `signal_generator.py` 时注意以下两点：**

1. **未来 7 天数据提取，严格使用全局交易日历做 `reindex`，防止停牌穿越。**
2. **15 分钟数据按日期时间戳安全拼接（找不到就赋 0）。**

那么，新架构跑出的 `master_signals.csv` 将会比你之前跑的更加精准，而且你后续无论怎么修改 `MFE*60%` 止盈、增加任何资金管理规则，回测时间都会从 **几小时 缩短到 0.1秒**。这是绝对值得的架构跨越！
